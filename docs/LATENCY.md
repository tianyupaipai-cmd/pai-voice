# 把通话延迟压下来：做了哪几步、为什么快了

这里只写思路，不附实现。每一步都要按自己的设备、网络和声音去试，数值没有通用答案。

一轮话的时间大致是：**对方说完 → 判断说完了 → 转写 → 回复端想 → 合成第一句 → 第一句传到手机开始播**。下面每一步都在砍其中一段。

## 1. 更早知道「这一句说完了」

- 静音判断不要太保守：结尾静音阈值从「宁可多等」调到「刚好不切断正常停顿」，每轮能省下几百毫秒。
- 对方还在说时不急着送：已经说出口的片段先攒着，等整句结束一起交，避免回复端回到一半又被下一段推翻。

## 2. 转写用快的那一档

- 优先用响应快的云端转写（一句话几百毫秒内出结果），本地模型只做兜底：云端失败或超时就当场换本地，通话不卡。
- 只转写这一句的音频，不带前文，请求小、返回快。

## 3. 回复直接送到回复端，不绕路

- 每一句转写完立刻递给终端里的 Agent（递进终端，或写进它盯着的文件），不经过轮询、不攒批。
- Agent 不用等整段写完：想好第一句就先发，后面的一句一句接着发。核心收到一句就开始合成，所以「说第一句」和「想后面的话」是并行的。
- 对方连着说几句时不互相掐断：每句各自递过去，回来的话按顺序排队念。

## 4. 合成：本地、常驻、流式

- 用本地 TTS，进程常驻、模型和参考音的特征开机就加载好、留在内存里，省掉每句的冷启动和网络往返。云端 TTS 只做兜底。
- 流式合成：一句里先合出来的那一小段就先发，每一段都是能独立解码的音频，客户端收到一段就排进播放队列，不用等整句合完。
- 第一句不等：第一句一拿到就合成、就发；后面的句子跟着播放进度走——估一下手机那边还要播多久，快播完前一点点再合下一句。这样首音不变慢，被打断时后面那些也不会白合。

## 5. 传输和播放

- 音频用体积小、手机直接能解的编码（例如低码率 mp3），一句一小块地推。
- 等回复的那一两秒先放一个很短的应答音，听感上不是一片空白。
- 断线不等于挂断：网络闪断后一段时间内重连回来还是同一通，回复送到新连接上，不用重新开场。

## 6. 量出来再调

- 每一轮都记几个时间点：说完、转写完成、回复端第一句到达、第一段音频发出。看日志就知道慢在哪一段，而不是凭感觉改。
- 我们自己的经验：最慢的一段通常是「回复端想」和「合成第一句」；前者靠让 Agent 先说第一句，后者靠本地常驻 + 流式。
